## 1. 首 token P95

- **定义**：从 POST `/api/chat/stream` 发出到收到首个含 token 文本的 SSE `data:` 的耗时；同步记录终态（done/error）与事件序列。
- **方法 A（live 真容器）**：`httpx.stream` POST（`x-internal-token: dev-internal-token-change-me`），N=5，容器已热机。原始输出：5 次事件均为 `["trace","trace","error"]`，首包 185.1/36.4/44.8/32.9/42.9ms，终态 error 在 6556/2574/2579/2358/2376ms。token 事件 0 个——空 key 下 plan 节点真实 LLM 调用失败，网关逐级降级后 `_事件流` 回 error，无真实首 token 可采。
- **方法 B（假模型引擎开销）**：venv 内驱动 `_事件流`，`构建分析图谱(基础模型=FakeListChatModel)`，检查点落 `/tmp` 临时库，每轮独立会话号（无缓存命中），N=20。原始输出：20/20 命中 token 且 done；首 token 均值 10019ms、P50 8352ms、P95 17424ms、min 7267ms、max 21761ms；端到端均值 10034ms、P95 17459ms。
- **归因**：单轮内 planner 做一次 `混合检索`， warmed 状态下 embedding 编码约 14ms、向量召回约 68ms、全文约 37ms、CrossEncoder CPU 精排 18 对约 11759ms——首 token 时间基本等于混合检索时间。冷启动另有 embedding 权重加载约 10s、重排权重加载一次。
- **标注**：方法 B 为引擎＋本地检索开销，**不含真实 LLM 计费与公网耗时**；真实 key 下的首 token 需重测。

## 2. 单轮成本

- **定义**：网关 `问答` 单次调用花费元＝（输入 Token＋输出 Token）/1000×单价（单价 0.002 元/千 Token，`模型网关` 默认值，生产阈值未动）。
- **方法**：venv 内 `模型网关(提供者列表=[兜底模板提供者()])`，N=20。原始输出：提供者恒为"兜底模板"、输入/输出 Token 恒 0、成本均值与 P95 均为 0.000000 元；网关耗时均值 25.4ms、P50 18.3ms、P95 37.3ms。
- **账本参照**（`模型调用账本` 真实行，实测前后对比）：回显提供者 39 行、均 0.000030 元/轮（10 in＋5 out）；兜底模板 35 行、0 元；语义缓存 1 行、0 元；累计约 0.00117 元。无"主模型/备选模型"行——空 key 下零真实调用。公式示例：500 in＋300 out 的真实轮次＝ 800/1000×0.002 ＝ 0.0016 元（估算，非实测）。
- **标注**：以上**不含真实 LLM 计费**；实测写入的 20 行 `ce-cost-*` 账本行已删除，账本恢复原状（另有 8 行并发写入非本轮产生，未动）。

## 3. 常驻内存

- **定义**：容器稳态 RSS 上限 proxy，以 `docker stats --no-stream` 的 MEM 为准。
- **方法**：3 次采样、间隔 20s（此前刚做过一次 live 问答使 ai 容器完成 embedding 加载，属热机稳态）。
- **原始输出**：ai 922.9/922.9/922.9MiB；backend 436.3/436.6/436.0MiB；frontend 11.64/11.53/11.57MiB；tts 60.26/59.79/60.05MiB；vector-postgres 62.96/64.30/64.12MiB；mysql8 约 460MiB；kafka 约 1GiB；redis 约 6MiB。
- **补充**：ai 容器冷启动（embedding 未加载）约 241.9MiB，加载本地 embedding 后涨至 922.9MiB 并保持稳定——内存预算应按热机态计。

## 4. 检索 P95

- **定义**：PG 真实查询耗时（不含首次模型加载）。
- **方法**：venv 直连 `postgresql://postgres:***@localhost:55433/love_memory`，`HF_HUB_OFFLINE=1`。
  - 全文召回：20 个真实查询词轮询（含"数据/报表/同步失败如何排查"等），N=100。原始输出：均值 18.94ms、P50 16.78ms、P95 29.01ms、min 15.85ms、max 41.11ms。
  - 向量召回：本地 embedding 热机后固定向量查 20 条，N=30。原始输出：均值 63.64ms、P50 60.18ms、P95 72.18ms、min 59.52ms、max 79.97ms；单次编码约 14ms。
  - 混合端到端：双模型热机后，N=10。原始输出：均值 13226ms、P50 12504ms、P95 15544ms、min 11009ms、max 18620ms，平均命中 5/5，首来源"产品手册.md"。分解实测：向量 68ms＋全文 37ms＋精排 11759ms（18 对）——CPU 精排占约 99%。
- **缓存/降级说明**：全部直连无应用缓存；向量/混合依赖本地权重（有则用，无则抛异常降级纯全文——本次权重齐备未触发降级）。

## 5. 编排单节点开销

- **定义**：`编排引擎.运行` 全链路耗时（校验→版本落库→跑图→SQLite 执行/跨度落库→PG 跨度双写），流程为 开始→代码（表达式 `1+1`）→结束。
- **方法**：venv 内 SQLite 落 `/tmp` 临时库（PG 双写保持真实），5 次热身＋N=100。原始输出：均值 73.94ms、P50 73.01ms、P95 93.43ms、min 61.30ms、max 116.67ms。
- **说明**：该数字是"单节点流程整轮开销"而非纯表达式求值（纯 `安全求值` 为微秒级）；含每次 `保存版本` 自增与 3 个跨度的 SQLite＋PG 双写，属生产真实路径。

## 6. 画布 100 节点 LCP（本地近似，方法注明）

- **方法（非真实 LCP）**：Node 复刻 `编排页.tsx` 的节点构造逻辑（8 类节点轮替、5 列网格坐标、label、边连接）＋渲染前 `nodes.map` 样式映射＋`JSON.stringify`，N=50。另测前端静态页 TTFB（curl，N=20）作对照。真实 LCP/INP/CLS 需浏览器采集，已跳过。
- **原始输出**：100 节点数据准备均值 0.22ms、P50 0.15ms、P95 0.66ms、min 0.11ms、max 1.05ms，JSON 约 16.5KB；`GET /` TTFB 均值 3ms、P95 4ms（min 2ms、max 9ms）。
- **结论**：100 节点下数据层与首字节开销可忽略，真实 LCP 瓶颈应在浏览器端 ReactFlow 布局/绘制，需 Lighthouse 实测补齐。
