# SQL 优化记录（实测，源库 PostgreSQL，EXPLAIN ANALYZE）

> 数据规模：用户 120 行，角色 200 行，消息 8000 行。结论先行：小表上绝对耗时均为毫秒噪声，优化价值在结构（扫描次数/计划节点），等价性逐行 diff 验证。

## 优化 1：统计概览 5 标量子查询 → 单遍 CTE 交叉连接

- 改动：`源统计Mapper.统计概览`，5 个 `SELECT COUNT(*)`（用户表被全扫 2 次）→ 每表只扫一次＋`FILTER` 一次算出 24 小时新增。
- 优化前：5 个 InitPlan，`Seq Scan on 用户 ×2`，Execution 0.672ms。
- 优化后：3 次扫描（用户/角色各 1 次，消息索引），11 行计划。
- 等价性：`120|200|8000|0|0` 两边完全一致。

## 优化 2：用户趋势相关子查询 ×90 → 窗口累计

- 改动：`源统计Mapper.统计用户趋势`，每天一次相关子查询（`SubPlan loops=90`）→ 起点基数 CTE＋`SUM() OVER (ORDER BY)`。
- 优化前：Execution 4.662ms，SubPlan 循环 90 次。
- 优化后：Execution 0.912ms（约 5 倍），无 SubPlan。
- 等价性：90 行逐行 diff 完全一致。

## 优化 3：留存聚合 3 路自连接 → 单次条件聚合

- 改动：`源统计Mapper.统计留存聚合`，d1/d3/d7 三个用户×消息连接 → 一次连接＋`COUNT(DISTINCT) FILTER`。
- 优化前：计划 56 行，Execution 9.830ms。
- 优化后：计划 28 行（减半），Execution 9.938ms（持平：小数据下哈希聚合主导；数据放大后单次扫描优势显现）。
- 等价性：90 行数值逐项相等（仅 `0` 与 `0.00` 显示差异，Java 侧均为 double 0.0，下游 JSON 一致）。

## 未采用：消息趋势日期谓词下推

- 实验：在内层加 `创建时间 >= 窗口起点`（有 `idx_消息_创建时间`）。
- 结果：2.583ms → 2.952ms，无提升。原因：种子数据全部落在 90 天窗口内，谓词过滤不掉任何行，仍是全表扫描。保持原 SQL 不动。
