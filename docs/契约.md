管理中心直连和我恋爱吧同一套库，读写分离管理一切数据：读走分页参数化查询加PII视图掩码（列表默认掩码手机号，详情解密记审计），写入一律走事务＋审计留痕；禁自动补生产库（生产环境启动前补齐禁用）。

权限矩阵唯一真源是 `管理后端/src/中间件/管理员.ts::角色能力矩阵`（能力位 `cha_kan`/`feng_jin`/`feng_jin_shen_he`/`tong_ji_xie`/`gao_we`），
门禁与 `GET /api/guan-li/wo-de-jiao-se` 回传的能力同源，前端菜单按该能力位过滤条目。
FP-17 落地现状（用户裁决 L-27 按首行口径扩权）：超级管理员=五位全量，运营=`cha_kan`+`feng_jin`+`tong_ji_xie`，审核员=`cha_kan`+`feng_jin_shen_he`。
门禁口径：封禁/解封写需 `feng_jin`（运营/超级管理员），封禁申诉审核需 `feng_jin_shen_he`（审核员/超级管理员），统计族（`/tong-ji/*` 含读审计写侧）需 `tong_ji_xie`（运营/超级管理员）；
授予角色/回收角色/接管角色/结束接管/审核新建评审处理多项/三类发布仍 `gao_we` 超级管理员专属；其余角色越权一律 403。

## 一、鉴权流程

管理登录链：`POST /api/guan-li/deng-lu {shou_ji_hao, mi_ma, chi_jiu_hui_hua}` → 同库验密码哈希（bcrypt）→
按 `管理员/运营/审核员` 三旗标解析角色（任一为真即可登录，全伪 403 `WU_GUAN_LI_QUAN_XIAN` 且不签发令牌）→
同 `JWT_SECRET` 签发管理令牌（载荷含 `jiaoSe` 回显位，授权一律不取它）→ 响应体回传
`{yong_hu_id, yong_hu_ming, jiao_se, neng_li}` → 后续接口 `Authorization: Bearer <管理令牌>`
或安全 Cookie → 同源验签（HS256 白名单）→ 过期检查 → 黑名单检查 → 按用户吊销检查 →
管理员门禁（查库三旗标）→ 能力门禁（查库角色的能力位含该路由所需位；高危写需 `gao_we`，FP-17 起封禁需 `feng_jin`、封禁申诉审核需 `feng_jin_shen_he`、统计族需 `tong_ji_xie`）。
刷新 `POST /api/guan-li/shua-xin` 每次按查库角色重新签票，角色被回收即 401。
FP-03 会话生命周期（Cookie 双名/作用路径/Redis 前缀的唯一真源在 `管理后端/src/会话.ts`）：
「记住密码」经 `chi_jiu_hui_hua`（线路键唯一真源，只认 JSON 布尔真值，驼峰或字符串/数字等其它形态一律按会话级处理）
决定持久档——持久会话刷新 Cookie 带 `Max-Age=刷新有效秒`，非持久回落为浏览器会话级 Cookie（关窗即失效）；
持久标记只存服务端 Redis（`guan_li_shua_xin_chi_jiu:{刷新编号}`），不落到客户端可伪造位；
刷新号为一次性轮换（旧号 `del` 后才 `set` 新号），故并发两次续期第二次必 401，前端续期以单飞（in-flight 复用同一条 Promise）保证同一浏览器同时只发一次；
访问令牌 Cookie 的 `Max-Age` 与 `JWT_EXPIRES_IN` 同源折算秒数（`访问令牌有效秒`），不再各处写死 15 分钟。
注销 `POST /api/guan-li/tui-chu`（挂认证＋管理员门禁同层，任何已认证管理员可终结自己的会话，不需要业务能力位）：
按 `jti` 写 `jwt_blacklist:{jti}` 吊销当前访问令牌至其自然过期、删除当前刷新号，并清发双 Cookie；
只吊销本次令牌，不写按用户吊销键（不影响该账号其它会话），重复注销为 401 `LING_PAI_WU_XIAO` 而非 500。
兼容链：和我恋爱吧签发令牌仍可只校验通行（无 `jiaoSe` 声明，门禁照常查库定角色）。
Socket 握手与 HTTP 同源：`handshake.auth.token` 携带同一签发令牌，
握手期验签加按用户吊销检查，已连接套接字挂载吊销守卫，
吊销后存量连接直接断开。
语音合成走双轨：用户 Bearer 令牌或服务间 `X-Internal-Token` 任一通过即放行。

签发方为管理后端（管理登录）与和我恋爱吧（用户登录）两处，同 `JWT_SECRET` 同源互认。

| 字段 | 说明 |
| ---- | ---- |
| yongHuId | 用户编号，管理中心取身份首选 |
| shouJiHao | 用户手机号 |
| jiaoSe | 管理令牌回显字段（`chao_guan`/`yun_ying`/`shen_he_yuan`），仅用于首屏展示；服务端一律按用户编号查库三旗标重新解析角色，该字段不是授权依据 |

## 三、ADMIN_PHONES

逗号分隔手机号白名单，仅作一次性初始化引导名单，
需 `BOOTSTRAP_ADMIN=1` 触发启动种子，把已注册账号提权为管理员。
运行期管理员判定一律以用户表管理员字段为准（变更即失效广播），
不以该白名单实时判定。管理中心侧同名引用该键，不自备名单。

## 四、黑名单与按用户吊销

`jwt_blacklist:{jti}`：值为 1，存活期等于令牌剩余有效期；命中即拒。
管理端唯一写入方是 `POST /api/guan-li/tui-chu`（`管理后端/src/会话.ts` 的登出路由，按当前令牌 `jti` 写入到其自然过期），
改密侧的写入归和我恋爱吧端；读侧检查在 `管理后端/src/中间件/认证.ts`。
`jwt_yong_hu_cheXiao:{yongHuId}`：值为签发毫秒时间戳，存活期为令牌最大有效期 7 天；
判定式为签发时刻小于等于该值则拒，签发时刻取 `qianFaHaoMiao`，缺失时回退 `iat` 乘 1000。
管理端写入方是「回收角色」（`路由/管理写.ts`，YH-108 改完权限不等令牌自然过期）与
「提交封禁且命中的是被处置账号」（`路由/封禁.ts`），两处与读侧一律引 `会话.ts::按用户吊销前缀`，
不得再手写键名字面量（由 `管理后端/tests/单元/会话.test.ts` 的「FP-07 会话线路键与缓存前缀单源」锁死）。
语音服务降级语义：未配 `REDIS_URL` 时跳过吊销检查（本地开发降级，
生产必须同源配置）；已配但不可用时拒绝请求。

## 五、限频

和我恋爱吧侧统一经 Redis 计数，多实例共享：管理操作 10 次每分、
聊天 30 次每分、AI 请求 15 次每分、常规 100 次每分、
登录与发码另有账号加 IP 双层限流。
限流键策略：已认证按用户编号，未认证按可信链路推导的真实来源 IP。
语音服务保留进程内滑动窗口限流：默认每身份 60 次每 60 秒
（`TTS_RATE_LIMIT` 与 `TTS_RATE_WINDOW_SECONDS` 可配），超限 429。
管理后端限频待 FP-04 按本表管理档实施。

## 六、错误码

管理接口失败体统一为 `{cheng_gong:false, shu_ju:null, code, message, traceId, retryable, retryAfterMs?, fieldErrors?}`；`code` 为稳定注册表码，`message` 为中文，`traceId` 可追到脱敏日志。401 未授权两种码：缺头或格式错误为 `WEI_SHOU_QUAN`，验签失败、过期、命中黑名单、命中用户吊销均为 `LING_PAI_WU_XIAO`；403 为已认证但无管理身份或权限不足；404 为记录不存在；409 为状态冲突；429 为限流 `XIAN_LIU` 并带 `retryAfterMs`。依赖不可用、业务失败和 `/api/ready` 健康检查失败也使用同一注册表，不产出无码响应。语音服务失败体为中文 `{"提示": "..."}`，文案走 `app/文案.py`：缺凭证、令牌无效或过期、请求频繁三档。

## 九、管理接口鉴权头规范

管理接口统一要求 `Authorization: Bearer <管理令牌>`（管理后端 `/api/guan-li/deng-lu` 签发）或 httpOnly 安全 Cookie 二选一，
`管理前端` 自 FP-03 起只走 Cookie（原生 fetch 的 `credentials:'include'`，令牌零落盘、请求层不拼 `Authorization` 头），
Bearer 通道为命令行/第三方调用与和我恋爱吧签发端保留；
和我恋爱吧签发令牌兼容只校验通行，管理员门禁按第三、四节执行（查库复核三旗标定角色，`guanLi`/`jiaoSe` 声明一律不单独授信）。
`X-Internal-Token` 仅用于服务间调用，不作为管理前端凭证。

## 十五、管理端错误码表（FP-07/FP-15）

码的唯一真源是 `管理后端/src/错误码.ts::错误注册表`；`错误码` 只是由注册表派生的兼容别名，路由、中间件与响应层禁止手打未注册字符串。构造规则=失败语义的拼音全大写、下划线分词，不含中文、不含版本号、不随措辞变化（YH-025：状态与分类由码决定，禁止用文案子串推状态码）。码一经发布不得改名；改提示文字不动码。新增或修改码必须同批改注册表与本表，否则后端文案守卫判红。

失败响应的规范字段为 `{cheng_gong:false, shu_ju:null, code, message, traceId, retryable, retryAfterMs?, fieldErrors?}`。`message` 必须是管理员可见中文；`code`、`message`、`traceId`、`retryable` 必填。`retryAfterMs` 只用于 429，`fieldErrors` 只承载机器字段到中文提示的映射。兼容字段 `ti_shi` 与 `cuo_wu_ma` 仍与 `message`、`code` 同值输出，但新前端只读取规范字段。

追踪规则：首个请求中间件从 `X-Request-Id`、`X-Trace-Id` 或 `traceparent` 读取符合 `[A-Za-z0-9._:-]{1,64}` 的值，否则生成 `nei-sheng-*`；同一值写入 `X-Request-Id`、`X-Trace-Id` 与失败包络 `traceId`。前端每次请求生成独立 `qian-duan-*` 追踪号，包络追踪号优先、响应头次之、请求号兜底。SQL、堆栈、路径、环境、驱动与第三方原文只进脱敏日志；日志递归移除密码、Cookie、令牌、API key 与授权值。

重试规则：`retryable=true` 的错误才显示“重试当前操作”；401 会话、403 权限、参数/审批缺失与不存在错误不显示重试。409 冲突须刷新状态后由用户决定；429 必须保留 `retryAfterMs`。页面切换、卸载或同一页面发起新请求后，旧批次错误不得覆盖新页面；错误态存在时不得渲染空态。服务端错误、业务错误、依赖错误和健康检查失败均走同一注册表与失败包络出口。
