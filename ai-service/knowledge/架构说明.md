# 恋爱吧数据中心 架构说明

## 总体链路

```
和我恋爱吧 业务库(PostgreSQL, 只读)
        │ 定时调度(默认每300秒) / 手动触发
        ▼
   Kafka topic: love.sync.events (KRaft 单节点)
        │ 消费聚合(按 batchId 幂等，失败重试2次后进死信队列 DLT)
        ▼
分析库 MySQL (love_analytics) ── Redis 缓存(穿透/击穿/雪崩三防)
        │
   Spring Boot API (:8080)
   ├─ /api/v1/**  面向运营大屏(JWT 鉴权)
   └─ /api/internal/stats/**  面向 AI 服务(X-Internal-Token 鉴权)
        │                          │
   运营大屏(:5174)           AI 分析助手(ai-service :8000)
```

## 各层职责

### 1. 业务库（源库）

「和我恋爱吧」线上业务的 PostgreSQL 库，承载用户、角色卡、消息、好感度、游戏档案等业务表。数据中心通过只读账号访问，绝不写入；分析查询一律不直连业务库。演示环境使用导入真实表结构基线 + 程序生成演示数据的副本容器（端口 55432）。

### 2. Kafka 同步管道

Java 后端的定时任务把「同步指令」发到单一 topic `love.sync.events`（含批次号 batchId 与统计类型列表）。消费者收到指令后从源库执行 SQL 聚合，把结果 UPSERT 到分析库。Kafka 起到解耦（源库故障时指令堆积不阻塞调度）、削峰与可回放的作用；失败消息重试 2 次后进入 `love.sync.events.DLT` 死信主题并记录 sync_log。

### 3. 分析库 MySQL

消费者聚合写入的统计快照：总量概览、每日注册趋势、每日消息趋势、好感度阶段分布、人设标签热度、挑战排行、AI 用量趋势、同步日志。大屏与 AI 服务读的都是分析库，避免影响线上。

### 4. Spring Boot API

对外统一返回 `{code, message, data}` 结构：

- `/api/v1/**`：面向大屏，JWT 鉴权（管理员登录），统计接口带 Redis 缓存三防；
- `/api/internal/stats/**`：面向 AI 服务，请求头 `X-Internal-Token` 匹配环境变量 `INTERNAL_TOKEN`。当前可用端点：

| 端点 | 说明 |
| --- | --- |
| /api/internal/stats/overview | 平台总量概览（累计用户、角色卡、消息总数等） |
| /api/internal/stats/users/trend?days=N | 近 N 天每日新增注册趋势 |
| /api/internal/stats/messages/trend?days=N | 近 N 天每日消息量趋势 |
| /api/internal/stats/favorability/distribution | 关系阶段分布 |
| /api/internal/stats/persona/ranking | 人设标签热度排行 |
| /api/internal/stats/challenge/rank | 挑战完成排行 |
| /api/internal/stats/ai-usage/trend?days=N | 近 N 天 AI 用量趋势 |

同步链路状态由 `/api/v1/sync/status` 提供（需管理员 JWT）。

### 5. 运营大屏

React + ECharts 页面（端口 5174），轮询 `/api/v1/*` 渲染指标卡片与趋势图。

### 6. AI 分析助手（ai-service）

Python FastAPI 服务（端口 8000），基于 LangGraph 编排 ReAct Agent：

- 工具层封装上述内部 API 与知识库 RAG 检索（ChromaDB 向量库）；
- LLM 通过 OpenAI 兼容协议接入 DeepSeek；
- 对外提供 `POST /api/chat/stream` SSE 流式接口，另以 MCP stdio Server 形式把同样的查询能力开放给外部 AI 客户端。

AI 服务同样是只读视角，不具备任何写库权限，最小权限原则。
